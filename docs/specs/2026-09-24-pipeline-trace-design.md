# pipeline-trace: водопад длительности GitLab-пайплайнов

Дата: 2026-09-24. Статус: дизайн утверждён, реализации нет.

## Что это

`pipeline-trace` — CLI-утилита на Node 22 без runtime-зависимостей. Она читает GitLab-пайплайн через GraphQL API и собирает один самодостаточный HTML-файл с водопадом в стиле трейсов Sentry: пайплайн → стейджи → джобы → downstream-пайплайны.

Отчёт отвечает на три вопроса:

- сколько длится пайплайн целиком;
- сколько проходит от старта пайплайна до конца стейджа X;
- какие джобы определили это время (критический путь).

Работает с любым проектом на любом GitLab-хосте, к которому у пользователя есть доступ. От CI-конфига конкретного репозитория не зависит.

## Границы

Входит:

- режим одного пайплайна;
- режим агрегата по N пайплайнам одного `ref` с переходом в любой из них;
- downstream-пайплайны (`trigger:`) вложенным поддеревом;
- критический путь по `needs`.

Не входит:

- GitHub Actions и другие CI. Модель спанов от источника не зависит, адаптер добавим, если понадобится;
- публикация в npm. Ставится из git-репозитория;
- терминальный вывод водопада;
- экспорт в Chrome Trace / Perfetto;
- виртуализация строк в HTML. Добавим, если появятся пайплайны на тысячи джоб.

## Запуск

```
pipeline-trace <url-пайплайна|url-MR>
pipeline-trace --project group/name [--ref master] [--source merge_request_event] --last 50
  [--status success,manual|any]
  [--host gitlab.example.com] [--out trace.html] [--no-open]
```

- URL пайплайна (`https://<host>/<group>/<project>/-/pipelines/<id>`) открывает режим одного пайплайна.
- URL MR открывает режим одного пайплайна для `head_pipeline` этого MR.
- `--project` + `--last N` открывают агрегат по последним N пайплайнам. `--ref` фильтрует по ветке, `--source` — по источнику. У MR-пайплайнов ref свой у каждого MR (`refs/merge-requests/<iid>/head`), поэтому агрегат по MR задаётся через `--source merge_request_event`.
- Хост берётся по порядку: из URL, из `--host`, из `glab config get host`. Если ни один источник не дал хост, утилита завершается с ошибкой.
- Токен берётся по порядку: `glab config get token --host <host>`, затем `GITLAB_TOKEN`. `GITLAB_TOKEN` отправляется только на известный хост: совпадающий с `GITLAB_HOST` или с хостом `glab` по умолчанию. Иначе ссылка от постороннего человека увела бы токен на чужой сервер. Если токена нет, ошибка объясняет оба способа его задать.
- Хост должен соответствовать `^[a-z0-9.-]+(:\d+)?$`.
- `--status` — список статусов через запятую, по умолчанию `success,manual`. Пайплайн, который остановился на ручной джобе (например, `deploy_prod`), GitLab помечает `manual`. В `litres/monorepo` так заканчиваются все полные пайплайны master и MR, а `success` на master получают короткие Publish-пайплайны из одной джобы. Для агрегата по master без Publish-пайплайнов используй `--status manual`. С `any` фильтра нет. Сводка показывает, сколько пайплайнов в каждом статусе.
- `--out` по умолчанию `pipeline-trace-<project>-<id|ref>.html` в текущем каталоге. Без `--no-open` утилита открывает файл в браузере.

## Данные из GitLab

Для каждого пайплайна утилита запрашивает через GraphQL:

- у пайплайна: `id`, `iid`, `createdAt`, `finishedAt`, `status`, `ref`, `path`;
- у джобы: `name`, стейдж, имя группы (для шардов `parallel`), `status`, `startedAt`, `finishedAt`, `queuedDuration`, `retried`, `webPath`, `previousStageJobsOrNeeds`, у bridge-джоб — `downstreamPipeline`.

`previousStageJobsOrNeeds` возвращает `needs` джобы, если они заданы, а иначе все джобы предыдущего стейджа. Поэтому граф зависимостей получается точным для конкретного пайплайна без разбора YAML. Зависимости приходят **именами** джоб. Модель сопоставляет имя с актуальной (не `retried`) попыткой джобы в том же пайплайне. Имена, которых нет в пайплайне, отбрасываются.

Правила запросов:

- джобы загружаются страницами по 100 через `pageInfo`, не больше 50 страниц; больше 5000 джоб — ошибка;
- downstream загружается не глубже 3 уровней;
- одновременно выполняется не больше 4 запросов;
- downstream-пайплайны загружаются рекурсивно;
- на 401/403/404 утилита выводит ошибку с хостом и путём проекта и завершается с ненулевым кодом.

Проверено 2026-09-24 на `gitlab.litres.io` (GitLab 19.2.6): все перечисленные поля, `pipelines(ref, source)`, `mergeRequest.headPipeline` и `kind: BUILD | BRIDGE` работают. Несуществующий проект даёт `project: null`, неверный токен — HTTP 401. Интроспекцию (`__type`) сервер не выполняет и отдаёт кэшированную полную схему, поэтому версию поля проверяй реальным запросом.

## Модель: спан

```js
{
  id, kind: 'pipeline' | 'stage' | 'group' | 'job' | 'bridge',
  name,
  start, end,        // мс от createdAt корневого пайплайна
  queued,            // мс ожидания раннера, только у job
  status, url, allowFailure,
  attempts: [{ start, end, status }],  // прошлые попытки при ретраях
  deps: [id],        // из previousStageJobsOrNeeds
  children: [span],  // pipeline → stage → (group →) job; bridge → pipeline
}
```

Правила:

- Все времена, включая время джоб downstream-пайплайнов, отсчитываются от `createdAt` корневого пайплайна.
- У джобы `start = startedAt`, `end = finishedAt`.
- У стейджа `start` равен минимальному `start` его джоб, `end` — максимальному `end`. Длина стейджа — `end − start`. Величина «до конца стейджа» равна `end`.
- Шарды `parallel` одного стейджа (`name 3/10` или `name: [3]`) при двух и более шардах объединяются в спан `group` с именем без суффикса. Границы группы считаются так же, как у стейджа.
- У пайплайна `end` — максимум из `finishedAt` и `end` его стейджей. У пайплайна в статусе `manual` `finishedAt` пустой, остаётся `end` стейджей.
- У bridge-джобы `end` — максимум из её `finishedAt` и `end` downstream-пайплайна.
- Если пайплайн ещё идёт, у незавершённых джоб `end = now`, а отчёт помечается как `running`.
- **Ретраи.** Основной спан — попытка с `retried: false`. Прошлые попытки попадают в `attempts`.
- **`manual`, `skipped`, `created`** без `startedAt` получают `start = end = null`. Они остаются в дереве, но в водопаде и критическом пути не участвуют.
- **`failed` с `allow_failure`** учитывается как обычная джоба, отличается только цветом.

## Критический путь

Вход — дерево одного пайплайна и целевое множество джоб. Для всего пайплайна цель — все джобы, для «до конца стейджа X» — джобы стейджа X.

1. Выбрать в цели джобу с максимальным `end`.
2. Если это bridge-джоба, перейти внутрь downstream-пайплайна к его джобе с максимальным `end` и продолжить путь оттуда. Когда внутри downstream у джоб закончатся `deps`, вернуться к `deps` самой bridge-джобы.
3. Среди `deps` текущей джобы выбрать ту, у которой максимальный `end`, и сделать её текущей.
4. Повторять шаг 3, пока `deps` не опустеет.

Выход — упорядоченный список джоб и зазоры между ними. Зазор — разница между `end` зависимости и `start` следующей джобы, включая `queued`. Эти зазоры тоже задерживают пайплайн, поэтому их показываем отдельно.

При равных `end` выбирается джоба, которая раньше стоит в дереве отчёта (порядок по связям, затем по старту). Среди зависимостей при равных `end` — та, что раньше в `deps`. Так результат воспроизводим.

`critical-path.mjs` не импортирует других модулей. `render.mjs` подставляет его в HTML без изменений, поэтому интерфейс пересчитывает путь при клике по стейджу без второй реализации.

## Агрегат по N пайплайнам

- Узлы деревьев сливаются по ключу `kind + name` среди детей одного родителя. Так стейдж, группа шардов и джоба получают свой агрегат, а downstream-пайплайны агрегируются рекурсивно под своей bridge-джобой.
- Метрики джобы:
  - p50 и p90 для `start`, `end − start` и `queued`;
  - присутствие: в скольких из N пайплайнов джоба запускалась;
  - среднее число ретраев;
  - доля пайплайнов, где джоба лежала на критическом пути всего пайплайна.
- Метрики стейджа («до конца стейджа», длина) и общая длина пайплайна сначала считаются в каждом пайплайне отдельно, затем из них берётся перцентиль. Складывать перцентили джоб нельзя.
- Перцентиль считается методом nearest-rank по отсортированным значениям.
- Все N деревьев встраиваются в HTML. Из панели деталей можно открыть любой пайплайн в режиме одного пайплайна.

## Интерфейс HTML

Один файл с инлайновыми CSS и JS, данные встроены как JSON. Внешних запросов нет, поэтому файлом можно делиться.

- **Шапка.** Проект, ref, ссылка на пайплайн или строка вида «агрегат: 50 пайплайнов master, 47 success». Общая длина. Ось времени с делениями. В агрегате подписи полосок показывают p50 и p90 сразу, переключателя нет.
- **Левая колонка — дерево.** Кнопка ▸/▾ и число потомков у каждого узла. В строке стейджа: `длина 3m12s · до конца 14m05s`.
- **Центр — водопад.**
  - Полоски — `div` с `left` и `width` в процентах от оси.
  - Цвета: стейдж — жёлтый, джоба — по статусу, очередь `queued` — серый сегмент перед полоской, `allow_failure` — оранжевый, прошлые попытки — бледные.
  - Длительность подписана справа от полоски.
  - У джоб на критическом пути есть обводка, зазоры ожидания нарисованы пунктиром.
  - В агрегате сплошная часть полоски начинается в p50 `start` и длится p50 длительности, а «ус» дотягивает до p90 длительности. Разброс старта в полоску не входит: иначе задержка из-за чужих ретраев выглядит как медленная джоба.
- **Правая панель — детали по клику.**
  - Для одного пайплайна: имя, стейдж, статус, start/end, `queued`, длительность, `deps`, попытки, ссылка в GitLab.
  - Для агрегата: p50/p90, присутствие, доля на критическом пути, список значений со ссылками на пайплайны.
  - Пока панель открыта, водопад сужается на её ширину (на экранах от 900 px).
- **Управление.**
  - Клик по стейджу пересчитывает критический путь до конца этого стейджа.
  - Перетаскивание полосок с зажатой левой кнопкой сдвигает ось, но не левее начала пайплайна; сдвиг начинается после 4 px движения, поэтому клик по строке по-прежнему выделяет её.
  - Ctrl + колесо мыши масштабирует ось.
  - Esc закрывает панель.
- **Тема** светлая и тёмная через `prefers-color-scheme`.

## Связи между джобами

Добавлено 2026-09-24. Связь — это элемент `deps` спана: джоба ждала завершения другой джобы (`needs` или предыдущий стейдж).

### Порядок внутри стейджа

Функция `orderByDeps(children)` из `src/model.mjs` упорядочивает детей стейджа и детей группы шардов. Она же используется в агрегате.

1. Соседний узел-владелец зависимости — это сосед, который сам является зависимостью или содержит её (группа шардов). Зависимости вне этого набора соседей, например из других стейджей, на порядок не влияют.
2. Родитель узла — сосед-владелец, который закончился позже остальных. Зависимости группы — объединение зависимостей её шардов. При равном `end` родителем становится сосед, который раньше стоит в порядке по старту.
3. Корни — узлы без родителя. Они идут по старту. Сразу под каждым узлом идут его дети по старту, дальше рекурсивно в глубину.
4. Каждому узлу функция записывает поле `after`: id родителя или `null`.

Отступ не добавляется. После имени узла с `after` выводится приглушённая подпись `← <имя родителя>`.

### Связи в агрегате

У агрегированных узлов `job`, `bridge` и `group` есть `deps`: id агрегированных узлов, чьи исходные спаны были зависимостями хотя бы в одном пайплайне. Дети агрегированного стейджа упорядочиваются той же `orderByDeps` вместо сортировки по p50 старта.

### Подсветка

При выборе джобы, группы или bridge кликом подсвечиваются прямые связи из любого стейджа:

- зависимости выбранного узла — полоса слева цвета `--dep-up` и подпись в полосе `↑ нужна для <выбранная>`;
- узлы, у которых выбранный узел есть в `deps`, — полоса слева цвета `--dep-down` и подпись `↓ ждёт <выбранная>`.

Цепочка целиком не подсвечивается: её показывает критический путь.

### Линии связей

Каждая связь между видимыми строками рисуется ломаной со стрелкой в SVG-слое поверх водопада: от конца полоски зависимости вправо на 6 px, вертикально до строки зависимой джобы и до начала её полоски. Связь со свёрнутой группой идёт к строке группы; у раскрытой группы линии рисуют шарды. Джобы без старта линий не получают. В агрегате линия начинается в p50 старта + p50 длительности зависимости и заканчивается в p50 старта зависимой джобы. Обычные линии — `--muted` с прозрачностью 35%, связи выбранного узла — `--dep-up` и `--dep-down` толщиной 1,5 px поверх остальных.

Полоски, подписи и деления оси лежат во внутренней дорожке с отступами 12 px слева и 24 px справа. Если связанный узел лежит в свёрнутой группе, подсвечивается строка группы. Esc и кнопка закрытия панели снимают подсветку вместе с выделением. Цвета заданы токенами для светлой и тёмной темы.

## Тесты

`node --test`, без зависимостей.

- `model.test.mjs` — обезличенная фикстура реального GraphQL-ответа превращается в дерево. Проверяются границы стейджа, ретраи в `attempts`, `manual` без времени и отсчёт времени downstream от корня.
- `critical-path.test.mjs` — синтетические графы: цепочка, ромб, джоба без `needs`, путь через bridge в downstream и обратно, равные `end`.
- `aggregate.test.mjs` — перцентили, объединение шардов, «до конца стейджа» по каждому пайплайну (отличается от суммы перцентилей), присутствие, `deps` агрегированных узлов и порядок по связям.
- `order.test.mjs` — `orderByDeps`: цепочка, несколько зависимостей (родитель — закончившаяся последней), зависимость из другого стейджа не влияет, группа шардов как единица, поле `after`.
- `gitlab.test.mjs` — пагинация и ошибки 401/403/404 на подменённом `fetch`.

HTML-шаблон автотестами не покрывается. Его проверяем вручную на двух пайплайнах: `litres/monorepo` с downstream и шардами и одном проекте без `needs`.
