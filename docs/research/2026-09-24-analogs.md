# Аналоги pipeline-trace: обзор рынка

Дата обращения ко всем источникам: 2026-09-24.

## 1. Вывод

Прямого аналога нет. Ни один найденный инструмент не сочетает все свойства
pipeline-trace: water­fall-трейс пайплайна с ретраями в той же строке,
крит. путь через `needs`, агрегат p50/p90 с «долей в крит. пути», метрику
стабильности джобы и список «куда направить силы» — в одном офлайн-файле
без сервера.

Ближайшие частичные совпадения — два инструмента. GitLab Pipeline
Visualizer рисует water­fall одного пайплайна с крит. путём, но это
статическая веб-страница только для GitLab.com, без ретраев, агрегатов и
рекомендаций. Datadog CI Visibility ближе всего по набору идей (water­fall,
крит. путь, время в очереди, частичный трекинг ретраев), но это SaaS с
подпиской по $8 за коммитера в месяц и без агрегата p50/p90 по джобам в
явном виде.

Остальные инструменты закрывают только часть задачи: GitLab и
`gitlab-ci-pipelines-exporter` — агрегатные графики без трейса и крит.
пути; Buildkite/CircleCI/Trunk/BuildPulse — анализ нестабильности тестов,
а не пайплайна целиком, и почти все требуют своей CI-платформы, а не
self-hosted GitLab. Продолжать стоит: связка «water­fall + needs-крит.
путь + ретраи в строке + агрегат по N пайплайнов + рекомендации» как
цельный офлайн-инструмент под self-hosted GitLab на рынке не встречена.

## 3. Инструменты по отдельности

**GitLab CI/CD analytics.** Встроенная страница Analyze → CI/CD analytics
показывает число прогонов, медиану и 95-й перцентиль длительности, success/
failure rate. Данные агрегированы по всему пайплайну — нет разбивки по
джобе или стадии, нет крит. пути с временем, нет ретраев отдельной строкой.
Доступно во всех тарифах, работает на self-hosted.

**Граф `needs` в GitLab.** Отдельная визуализация DAG пайплайна помогает
увидеть зависимости и потенциальные блокеры, но это статический граф без
длительности каждой джобы и без построения крит. пути по факту (только по
структуре зависимостей).

**GitLab Value Stream Analytics / Dashboard.** Считает время от коммита до
продакшена (Ultimate), не про длительность самого пайплайна CI, а про
цикл разработки целиком. Отношение к pipeline-trace косвенное.

**GitLab Pipeline Visualizer.** Внутренний инструмент команды Developer
Tooling в GitLab, статическая страница на GitLab Pages: вставляешь URL
пайплайна — получаешь water­fall с джобами, параллельными группами
(схлопнуты по умолчанию) и оранжевым блоком времени в очереди. Крит. путь
можно раскрыть. Это самый близкий по форме аналог single-pipeline вида
pipeline-trace, но без ретраев в строке, без агрегата по N пайплайнов и
без списка «куда направить силы». Инструмент выглядит привязанным к
GitLab.com (не проверено — поддержка self-hosted инстансов явно не
описана).

**Datadog CI Visibility (Pipeline Visibility).** Водопад/flame graph
пайплайна с фильтром по крит. пути, время в очереди, ИИ-анализ причин
падения джобы, повторный запуск джоб, классифицированных как «transient»
(шумные, не воспроизводимые). Поддерживает self-hosted GitLab начиная с
14.1 через встроенную интеграцию Datadog. Модель "трейс = пайплайн, спан =
джоба" ближе всего к идее pipeline-trace, но продукт — SaaS с подпиской
($8 за активного коммитера в месяц плюс доплата за превышение лимита
спанов), не офлайн-файл и не десктоп-приложение.

**Honeycomb buildevents + OpenTelemetry.** Универсальный подход: обернуть
каждый шаг CI в вызов `buildevents`, который шлёт спаны в OTel-коллектор
(Honeycomb или любой другой бэкенд). Даёт трейс сборки, но не показывает
граф `needs`, крит. путь считать не умеет сам — это ручная интеграция, а
не готовый продукт под GitLab.

**Нативный OTel-трейсинг в GitLab (issue 338943).** Предложение 2021 года
про end-to-end трейсинг сервера и раннера через OpenTelemetry с передачей
trace id между ними. По состоянию на 2025 год работа над темой не велась
(в тексте issue цитата: «Verify stage at GitLab is not working on tracing
with OpenTelemetry for CI/CD in calendar year 2025»). GitLab вместо этого
двигает точечные CI/CD observability-фичи через API. Идею можно
позаимствовать (модель span на этап/шаг), реализации ждать не стоит.

**gitlab-ci-pipelines-exporter + Grafana.** Prometheus-экспортёр метрик
GitLab CI (готовые дашборды для Grafana): длительность пайплайнов,
success/fail, метрики джоб. Чисто агрегатный взгляд по времени, без
water­fall конкретного пайплайна и без крит. пути. Полностью self-hosted,
но требует поднять и поддерживать Prometheus + Grafana + сам экспортёр —
то есть постоянную инфраструктуру, а не разовый анализ.

**gitlab_ci_viz.** Небольшой open source проект: живой GANTT-график джоб и
раннеров по нескольким проектам сразу, с картой загрузки раннеров
(runner contention). Работает с self-hosted GitLab через флаг
`--gitlab-url`, зависимостей кроме Python-stdlib и `glab` нет. Не считает
крит. путь, не показывает ретраи отдельно, агрегатов по многим пайплайнам
нет — это скорее живой монитор загрузки, чем трейс одного пайплайна.

**Buildkite Test/Pipeline Analytics, CircleCI Insights, Trunk CI
Analytics, BuildPulse.** Все четыре решают смежную, но другую задачу:
находят нестабильные (флаки) тесты и трекают их долю, время. У CircleCI
Insights есть p95-длительность по джобе/workflow — это ближе всего к
агрегату pipeline-trace, но только для CircleCI. Buildkite и Trunk
продвигаются в первую очередь под GitHub Actions/собственную платформу;
поддержка self-hosted GitLab как источника данных явно не подтверждена.
BuildPulse прямо пишет, что поддержка GitLab «скоро» — то есть пока её
нет. Ни один не строит water­fall пайплайна и крит. путь через `needs`.

**Foresight (Thundra), Harness CI/SEI, Meercode.** Foresight явно не
поддерживает GitLab (только GitHub Actions и TeamCity) — не конкурент.
Harness — тяжёлая enterprise-платформа: поддерживает self-hosted GitLab,
считает загрузку CI и умеет Test Intelligence (запуск только нужных
тестов), но это отдельная CI/CD-платформа или надстройка над ней, а не
инструмент для разового анализа конкретного пайплайна. Meercode —
похоже, заброшенный проект (сайт — парковочная страница на момент
проверки), исключён из дальнейшего сравнения.

## 4. Идеи, которые стоит позаимствовать

- **Оранжевый блок времени в очереди перед джобой** — GitLab Pipeline
  Visualizer рисует queue time визуально отдельным цветом в той же строке,
  что и саму джобу. У pipeline-trace уже есть сегмент очереди — стоит
  свериться, что цветовое кодирование так же однозначно читается.
- **Схлопывание параллельных групп по умолчанию** — тот же Pipeline
  Visualizer по умолчанию сворачивает шард-группы, разворачивая по клику.
  Совпадает с тем, что pipeline-trace уже делает для shard-групп —
  подтверждает, что это правильный дефолт.
- **ИИ-классификация «transient»-падений для авто-ретрая** — идея из
  Datadog CI Visibility: не просто показывать ретрай, а размечать его
  причину (шумный сбой инфраструктуры vs. реальный баг). Можно
  рассмотреть как расширение метрики «retried in k of N pipelines» —
  добавить категорию причины ретрая, если такие данные доступны через
  GraphQL.
- **Фильтр «показать только крит. путь»** — у Datadog это отдельный
  переключатель поверх trace view. Стоит проверить, useful ли в
  pipeline-trace toggle «скрыть всё, что не на крит. пути», отдельно от
  подсветки крит. пути.
- **Carrier для нескольких CI-провайдеров в одном дашборде** — Harness
  SEI и Meercode (хоть и мёртвый) держали в одном интерфейсе GitLab,
  GitHub Actions, Bitbucket и т. д. Для pipeline-trace не актуально сейчас
  (задача — self-hosted GitLab), но стоит держать в голове при
  проектировании форматов данных, если позже понадобится мультипровайдерность.
