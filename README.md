# Longpole

Показывает, на что уходит время пайплайна GitLab или GitHub Actions: водопад стейджей и джоб в стиле трейсов Sentry, критический путь и p50/p90 по многим пайплайнам. Результат — один HTML-файл без внешних запросов.

## Как читать отчёт

- Чипы в шапке: длина пайплайна (в агрегате — p50 · p90), время, потерянное на ретраях, и «можно сэкономить до» — сумма пунктов карточки «Куда направить силы». Кнопка `?` показывает клавиши и жесты.
- Карточка «Куда направить силы» — до трёх пунктов с экономией от 10 с. В неё попадают только джобы критического пути: остальные длину пайплайна не меняют. Клик по пункту выделяет джобу и прокручивает к ней.
- Каждый стейдж — карточка. В заголовке: `держит build:server +1m00s` — узкое место стейджа, затем `длина` (от старта первой джобы до конца последней) и `до конца` (от создания пайплайна до конца стейджа).
- Превышение: пунктирная вертикаль в карточке стейджа — момент, когда закончились все джобы, кроме последней. У последней джобы часть полоски правее вертикали заштрихована, подпись `+1m00s`.
- Ретраи: упавшие попытки нарисованы красной штриховкой в строке джобы, серая черта между ними — ожидание. Подпись `↻2 −8m29s` — число упавших попыток и потерянное на них время. В агрегате `↻ 3/8` — ретраи были в 3 из 8 запусков.
- Метка справа — стабильность джобы по пайплайнам агрегата: зелёная «стабильна», жёлтая «↻ k из N» — ретраи меньше чем в 30% запусков, красная — от 30%. В пайплайне, открытом по ссылке без агрегата, меток нет.
- Оранжевые полоски — критический путь. Клик по стейджу пересчитывает путь до его конца. Оранжевый пунктир — ожидание между джобами пути.
- Внутри стейджа джоба стоит сразу после соседа, которого ждала; подпись `← build:server` называет этого соседа. Зависимости из других стейджей на порядок не влияют.
- Клик по джобе подсвечивает её прямые связи из любого стейджа: `↑ нужна для` — джобы, которых она ждала, `↓ ждёт` — джобы, которые ждут её. Если связанная джоба в свёрнутой группе, подсвечивается группа. Esc снимает подсветку.
- Серая черта перед полоской — очередь раннера. В агрегате полоска начинается в p50 старта и длится p50 длительности, линия после неё дотягивает до p90. Полупрозрачная полоска — джоба запускалась не во всех пайплайнах; p90, число запусков и долю на критическом пути показывает панель деталей.
- Клик по строке открывает панель деталей. Сверху — вывод: сократит ли ускорение пайплайн, сколько можно сэкономить, есть ли ретраи. Дальше длительность, старт и конец (в агрегате p50 и p90), в агрегате — точка на каждый пайплайн (красная — с ретраями, клик открывает пайплайн), стабильность, кнопки связей ↑/↓ и самые долгие пайплайны со ссылками в GitLab.
- Трейс сдвигается перетаскиванием полосок мышью или клавишами `[` и `]`, но не левее начала пайплайна; ⌘/Ctrl + колесо или pinch на тачпаде меняет масштаб вокруг курсора, горизонтальный свайп сдвигает, `0` возвращает весь пайплайн.
- Клавиатура: ↑/↓ — соседняя строка, Enter — выбрать, ←/→ — свернуть и развернуть.

## Приложение

Форма строит отчёт по ссылке или по проекту из списка «Мои проекты». Приложение умеет:

- ссылку на пайплайн или MR GitLab, на run или PR GitHub — вставляешь в поле в шапке и жмёшь «Построить»; у PR строится самый долгий run head-коммита;
- «Мои проекты» в сайдбаре: добавление по ссылке на репозиторий, пайплайн или MR, по ssh-URL, по папке с клоном (читается `remote.origin.url`) или из списка проектов хоста; при добавлении проверяется доступ;
- токен запрашивается там, где понадобился: под полем ссылки или в диалоге добавления, со ссылкой на создание Personal Access Token (scope `read_api`); токены из `glab` и `GITLAB_TOKEN` приложение видит само; для GitHub — fine-grained token с правами Actions: read и Contents: read, токены `gh` и `GH_TOKEN`/`GITHUB_TOKEN` приложение видит само;
- вместо токена можно войти через OAuth: кнопка «Войти через <хост>» рядом с полем токена. GitHub показывает код для ввода на странице входа, GitLab открывает браузер и возвращает в приложение сам. Для github.com и gitlab.com ничего настраивать не нужно; чтобы видеть репозитории организации GitHub, владелец организации устанавливает на неё приложение [Longpole App](https://github.com/apps/longpole-app). Для self-hosted нужен Client ID своего приложения (см. ниже);
- экран проекта — ветка (с подсказками из списка веток), последние пайплайны с переходом в отчёт по клику и агрегат по N пайплайнам с фильтром по статусам; у проекта GitHub — выбор workflow: последние запуски и агрегат строятся по одному workflow;
- отчёт открывается в том же окне: «← Назад» или Esc возвращают к проекту, `Cmd/Ctrl+S` сохраняет HTML; последние 10 отчётов держатся в памяти, повтор из «Недавних» открывается без похода в GitLab;
- при запуске открывается последний проект;
- «Недавние» — история последних 20 запросов с повтором по клику, удалением записи или очисткой;
- настройки (шестерёнка, `Cmd/Ctrl+,`): хосты и токены с источником (связка ключей, `glab`, окружение), тема (системная, светлая, тёмная), язык берётся из системной локали (`ru*` — русский, иначе английский), переключатель RU/EN — в настройках;
- агрегат по статусам: пайплайн, остановившийся на ручной джобе, GitLab помечает `manual`; короткие служебные `success`-пайплайны (например, Publish-коммиты) смешиваются с полными — чтобы их отсечь, оставь только MANUAL;
- подсказки с жирафом появляются при первой встрече с элементом — диалогом, блоком токена, отчётом, панелью деталей; выключить и показать заново — в настройках, блок «Подсказки».

GitHub: пайплайн — один workflow run. Стейджи и критический путь строятся по `needs` из файла workflow на коммите запуска; без доступа к файлу отчёт строится одним стейджем. Перезапуск run рисуется как ретрай перезапущенных джоб. GitHub Enterprise Server определяется сам: по заголовку `X-GitHub-Enterprise-Version` или по `installed_version` в `/api/v3/meta`; ответы 5xx, 429 и 407 — ошибка, тип не запоминается; вставленная ссылка подсказывает тип только незнакомому хосту. В агрегате на сервер уходят только статусы SUCCESS и CANCELED, остальные фильтруются на клиенте. `gh` вызывается без токенов из окружения, `gh auth status` ждём не дольше 5 с.

Сборки — на странице [GitHub Releases](../../releases). Релиз выпускается вручную: Actions → release → Run workflow на `main`. Версия считается по коммитам с прошлого тега: `feat!:`/`fix!:` или `BREAKING CHANGE` → major, `feat:` → minor, остальное → patch. Источник версии — git-теги; `version` в `app/package.json` задаёт только первый релиз и дальше не обновляется.

| Система | Файл |
|---|---|
| macOS, Apple Silicon | `Longpole_<версия>_aarch64.dmg` |
| macOS, Intel | `Longpole_<версия>_x64.dmg` |
| Windows | `Longpole_<версия>_x64-setup.exe` |
| Linux | `Longpole_<версия>_amd64.AppImage`, `Longpole_<версия>_amd64.deb` |

Zip-архивов больше нет.

Установка без подписи:

- **macOS**: открыть `.dmg`, перетащить `.app` в «Программы». Первый запуск — «Открыть» из контекстного меню правой кнопкой мыши. Если Gatekeeper всё равно блокирует и это macOS 15 или новее — «Системные настройки» → «Конфиденциальность и безопасность» → «Всё равно открыть». Не помогло — снять карантин: `xattr -dr com.apple.quarantine "/Applications/Longpole.app"`.
- **Windows**: SmartScreen покажет предупреждение — «Подробнее» → «Выполнить в любом случае». Если в системе нет WebView2, установщик скачает его сам.
- **Linux**: для AppImage — `chmod +x Longpole_*.AppImage`; для deb — `sudo apt install ./Longpole_*.deb`.

Сеть: приложение доверяет сертификатам из системного хранилища и учитывает `HTTP_PROXY`/`HTTPS_PROXY`. Переменная `NODE_EXTRA_CA_CERTS` не поддерживается — корпоративный корневой сертификат надо добавить в системное хранилище.

Токен GitLab ищется в системной связке ключей, затем в `glab`, затем в `GITLAB_TOKEN` вместе с `GITLAB_HOST`. Токен GitHub — в связке ключей, затем в `gh`, затем в `GH_TOKEN`/`GITHUB_TOKEN` (github.com) или `GH_ENTERPRISE_TOKEN`/`GITHUB_ENTERPRISE_TOKEN` при `GH_HOST` (GHES). На Linux без Secret Service (`gnome-keyring`, KWallet) сохранить токен нельзя; используй `glab` или переменные окружения.

OAuth на self-hosted. GitLab: Edit profile → Applications → новое приложение, Redirect URI `http://127.0.0.1/callback` (именно `127.0.0.1`, не `localhost`), Confidential — снять, scope `read_api`; Application ID вставить в поле Client ID. GHES: Settings → Developer settings → GitHub Apps → новое приложение, Enable Device Flow, права Actions, Contents и Metadata на чтение; установить его на организации с нужными репозиториями, Client ID вставить в поле Client ID. Секрет приложения Longpole не нужен. Токен OAuth лежит в связке ключей там же, где PAT, и обновляется сам; если обновить его нельзя, запись удаляется и приложение снова попросит войти.

Токены, история, настройки и список проектов (`projects.json`) хранятся в каталоге данных приложения (у каждой ОС свой путь). Токены и история версии 0.1.0 (Electron) не переносятся.

Разработка (нужен Rust по `app/rust-toolchain.toml`, Node 22+):

```bash
cd app
npm ci
npm run build        # шаблон отчёта нужен сборке Rust
npm run tauri dev
```

Selfhosted в dev: сервер `cargo run -p longpole-server` с `url: http://localhost:5173` в `/etc/longpole/config.yaml`, фронт — `VITE_DELIVERY=selfhosted npm run dev`. Vite проксирует `/api`, `/auth` и `/healthz` на `localhost:8080`, Redirect URI OAuth-приложения — `http://localhost:5173/auth/callback/<domain>`.

Сборка установщика: `npm run tauri build`. Выпуск — автоматически по мержу в `main`; ручной запуск `workflow_dispatch` в Actions только собирает артефакты в прогоне, релиз не создаёт.

Проверки ядра: `cargo test -p longpole-core` в `app/`.

## Selfhosted

Веб-сервис для команды с GitLab self-managed или GitHub Enterprise Server: один инстанс в контуре организации, пользователи входят через OAuth своего хоста и смотрят отчёты в браузере. Базы нет: сессия лежит в зашифрованной cookie, кэш отчётов — в памяти процесса, «Мои проекты» и «Недавние» — в браузере. Бэкапить и мигрировать нечего.

### 1. OAuth-приложения

На каждый хост — одно приложение. Redirect URI выводится из конфига: `<url>/auth/callback/<domain>`, например `https://longpole.example.com/auth/callback/gitlab.example.com`.

- **GitLab:** Admin Area → Applications → New application. Redirect URI — как выше, Confidential включён, scope `read_api`. Application ID → `client_id`, Secret → `client_secret`.
- **GHES:** Settings организации → Developer settings → GitHub Apps → New GitHub App. Callback URL — как выше, «Expire user authorization tokens» включено, вебхук можно выключить. Repository permissions: Actions, Contents и Metadata — Read-only. Client ID → `client_id`, Generate a new client secret → `client_secret`; App ID не нужен. Приложение устанавливается на организации с нужными репозиториями.

### 2. Конфигурация

Ключ cookie — 32 случайных байта: `openssl rand -base64 32`. Смена ключа означает тихий повторный вход для всех.

Конфиг — один YAML-файл, в контейнере всегда по пути `/etc/longpole/config.yaml`:

```yaml
url: https://longpole.example.com   # публичный адрес, только https (кроме http://localhost) и только корень домена
cookie_key: ${LONGPOLE_COOKIE_KEY}
listen: 0.0.0.0:8080                # необязательно
cache_max_mb: 256                   # необязательно, лимит кэша отчётов
max_concurrent_builds: 8            # необязательно
build_timeout: 5m                   # необязательно, s | m | h
log:
  level: info                       # trace | debug | info | warn | error
  format: text                      # text | json
hosts:
  - domain: gitlab.example.com      # без схемы и пути, порт допустим; ходим всегда по https
    provider: gitlab                # gitlab | github
    client_id: 3f9a…
    client_secret: ${GITLAB_CLIENT_SECRET}
  - domain: github.example.com
    provider: github
    client_id: Iv1.…
    client_secret: ${GHES_CLIENT_SECRET}
```

Секреты в файл не пишутся: `${ИМЯ}` в любом месте файла подставляется из окружения контейнера, незаданная или пустая переменная — ошибка. Конфиг проверяется при старте: сервер печатает в stderr все ошибки сразу и выходит с ненулевым кодом. Изменения применяются рестартом. Логи — в stdout, `RUST_LOG` не читается.

### 3. Образ и запуск

Образ не публикуется — он собирается из тега релиза:

```bash
git clone --branch vX.Y.Z https://github.com/Phobym/longpole.git
cd longpole
docker build --build-arg VERSION=X.Y.Z -t longpole:X.Y.Z .
```

`VERSION` — версия, которую сервер пишет в лог при старте. В образе один файл `/longpole` на `distroless/static`, процесс работает от `nonroot` (uid 65532), порт 8080:

```bash
docker run -d --name longpole --restart unless-stopped -p 127.0.0.1:8080:8080 \
  -v /srv/longpole/config.yaml:/etc/longpole/config.yaml:ro \
  -e LONGPOLE_COOKIE_KEY -e GITLAB_CLIENT_SECRET -e GHES_CLIENT_SECRET \
  longpole:X.Y.Z
```

Файл конфига должен читаться пользователем 65532. `GET /healthz` отвечает `200 ok` без сессии и без обращений к хостам. `HEALTHCHECK` в образе нет — в distroless нет curl, проверку настраивает оркестратор (например, `httpGet` в Kubernetes).

**Инстанс работает в одну реплику**: обновление одноразового refresh-токена GitLab и кэш живут в памяти процесса. Рестарт теряет кэш, сессии в cookie переживают его.

### 4. Сеть

- **Прокси:** `HTTPS_PROXY` и `NO_PROXY` в окружении контейнера.
- **Корпоративный CA:** образ не меняется. Смонтируй PEM-файл и задай `SSL_CERT_FILE`. Файл **заменяет** системное хранилище образа, а не дополняет его: в нём должны быть и корпоративный CA, и публичные корни, если хосты за ними. Например, на Debian-хосте: `cat corp-ca.pem /etc/ssl/certs/ca-certificates.crt > /srv/longpole/ca.pem`, затем `-v /srv/longpole/ca.pem:/etc/longpole/ca.pem:ro -e SSL_CERT_FILE=/etc/longpole/ca.pem`.
- **Reverse proxy с TLS:** сервер слушает только HTTP, TLS завершает прокси или ingress. Деплой под подпутём не поддерживается — нужен отдельный домен. Прогресс построения отчёта приходит потоком, поэтому буферизацию ответов в прокси надо выключить. Rate limit на `/api/*` и `/auth/*` — тоже задача прокси или WAF.

```nginx
server {
    listen 443 ssl;
    server_name longpole.example.com;
    ssl_certificate     /etc/nginx/tls/longpole.crt;
    ssl_certificate_key /etc/nginx/tls/longpole.key;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_buffering off;
    }
}
```

### 5. Ссылка в CI

Заведи переменную `LONGPOLE_URL` со значением `url` из конфига: в GitLab — instance-level CI/CD-переменную (Admin Area → Settings → CI/CD → Variables), в GitHub — переменную организации (Settings организации → Secrets and variables → Actions → Variables). Пайплайны печатают по ней ссылку «Посмотреть в Longpole» на отчёт.

В ссылке вместо пути проекта — его числовой id: после переименования проекта ссылка по старому пути не открылась бы.

**GitLab.** Положи шаблон [`ci/gitlab/longpole.yml`](ci/gitlab/longpole.yml) в корень общего репозитория, например `ci-templates/longpole`, и подключи его в `.gitlab-ci.yml` проекта одной строкой:

```yaml
include: { project: ci-templates/longpole, file: /longpole.yml }
```

Шаблон добавляет в стадию `.pre` job `longpole`: он печатает ссылку в лог, а `environment:url` даёт кнопку в виджете MR. Без отдельного job хватит строки `echo` из шаблона в любом существующем job. Если GitLab работает на нестандартном порту, замени `$CI_SERVER_HOST` на `$CI_SERVER_FQDN`.

**GitHub и GHES.** Одна строка в любом job пишет ссылку в summary рана:

```yaml
- run: echo "[Посмотреть в Longpole](${{ vars.LONGPOLE_URL }}/${GITHUB_SERVER_URL#https://}/$GITHUB_REPOSITORY_ID/actions/runs/$GITHUB_RUN_ID)" >> "$GITHUB_STEP_SUMMARY"
```

Если старый GHES не задаёт `GITHUB_REPOSITORY_ID`, ссылка выйдет с пустым сегментом — подставь `$GITHUB_REPOSITORY`: ссылка заработает, но перестанет открываться после переименования репозитория.
