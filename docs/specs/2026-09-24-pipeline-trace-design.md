# pipeline-trace: водопад длительности GitLab-пайплайнов

Дата: 2026-09-24. Статус: дизайн утверждён, реализации нет.

## Что это

`pipeline-trace` — CLI-утилита на Node 22 без runtime-зависимостей. Она читает GitLab-пайплайн через GraphQL API и собирает один самодостаточный HTML-файл с водопадом в стиле трейсов Sentry: пайплайн → стейджи → джобы → downstream-пайплайны.

Отчёт отвечает на три вопроса:

- сколько длится пайплайн целиком;
- сколько проходит от старта пайплайна до конца стейджа X;
- какие джобы определили это время (критический путь).

Работает с любым проектом на любом GitLab-хосте, к которому у пользователя есть доступ. От CI-конфига конкретного репозитория не зависит.

## Границы

Входит:

- режим одного пайплайна;
- режим агрегата по N пайплайнам одного `ref` с переходом в любой из них;
- downstream-пайплайны (`trigger:`) вложенным поддеревом;
- критический путь по `needs`.

Не входит:

- GitHub Actions и другие CI. Модель спанов от источника не зависит, адаптер добавим, если понадобится;
- публикация в npm. Ставится из git-репозитория;
- терминальный вывод водопада;
- экспорт в Chrome Trace / Perfetto;
- виртуализация строк в HTML. Добавим, если появятся пайплайны на тысячи джоб.

## Запуск

```
pipeline-trace <url-пайплайна|url-MR>
pipeline-trace --project group/name --ref master --last 50 [--status success|any]
  [--host gitlab.example.com] [--out trace.html] [--no-open]
```

- URL пайплайна (`https://<host>/<group>/<project>/-/pipelines/<id>`) открывает режим одного пайплайна.
- URL MR открывает режим одного пайплайна для `head_pipeline` этого MR.
- `--project` + `--ref` + `--last N` открывают агрегат по последним N пайплайнам.
- Хост берётся по порядку: из URL, из `--host`, из `glab config get host`. Если ни один источник не дал хост, утилита завершается с ошибкой.
- Токен берётся по порядку: `glab auth token --hostname <host>`, затем `GITLAB_TOKEN`. Если токена нет, ошибка объясняет оба способа его задать.
- `--status` по умолчанию `success`. С `any` в агрегат попадают упавшие и отменённые пайплайны, а сводка показывает, сколько пайплайнов в каждом статусе.
- `--out` по умолчанию `pipeline-trace-<project>-<id|ref>.html` в текущем каталоге. Без `--no-open` утилита открывает файл в браузере.

## Данные из GitLab

Для каждого пайплайна утилита запрашивает через GraphQL:

- у пайплайна: `createdAt`, `startedAt`, `finishedAt`, `status`, `ref`, `webPath`;
- у джобы: `name`, стейдж, имя группы (для шардов `parallel`), `status`, `startedAt`, `finishedAt`, `queuedDuration`, `retried`, `webPath`, `previousStageJobsOrNeeds`, у bridge-джоб — `downstreamPipeline`.

`previousStageJobsOrNeeds` возвращает `needs` джобы, если они заданы, а иначе все джобы предыдущего стейджа. Поэтому граф зависимостей получается точным для конкретного пайплайна без разбора YAML.

Правила запросов:

- джобы загружаются страницами по 100 через `pageInfo`;
- одновременно выполняется не больше 4 запросов;
- downstream-пайплайны загружаются рекурсивно;
- на 401/403/404 утилита выводит ошибку с хостом и путём проекта и завершается с ненулевым кодом.

**Первый шаг реализации — пробный запрос к рабочему хосту.** Он проверяет, что `previousStageJobsOrNeeds` и `downstreamPipeline` есть в его версии GitLab. Если какого-то поля нет, запасной путь для `deps` — `needs` из конфига через REST `/projects/:id/ci/lint`.

## Модель: спан

```js
{
  id, kind: 'pipeline' | 'stage' | 'job' | 'bridge',
  name,
  start, end,        // мс от createdAt корневого пайплайна
  queued,            // мс ожидания раннера, только у job
  status, url,
  attempts: [{ start, end, status }],  // прошлые попытки при ретраях
  deps: [id],        // из previousStageJobsOrNeeds
  children: [span],  // pipeline → stage → job; bridge → pipeline
}
```

Правила:

- Все времена, включая время джоб downstream-пайплайнов, отсчитываются от `createdAt` корневого пайплайна.
- У джобы `start = startedAt`, `end = finishedAt`.
- У стейджа `start` равен минимальному `start` его джоб, `end` — максимальному `end`. Длина стейджа — `end − start`. Величина «до конца стейджа» равна `end`.
- У bridge-джобы `end` равен `end` её downstream-пайплайна.
- Если пайплайн ещё идёт, у незавершённых джоб `end = now`, а отчёт помечается как `running`.
- **Ретраи.** Основной спан — попытка с `retried: false`. Прошлые попытки попадают в `attempts`.
- **`manual`, `skipped`, `created`** без `startedAt` получают `start = end = null`. Они остаются в дереве, но в водопаде и критическом пути не участвуют.
- **`failed` с `allow_failure`** учитывается как обычная джоба, отличается только цветом.

## Критический путь

Вход — дерево одного пайплайна и целевое множество джоб. Для всего пайплайна цель — все джобы, для «до конца стейджа X» — джобы стейджа X.

1. Выбрать в цели джобу с максимальным `end`.
2. Если это bridge-джоба, перейти внутрь downstream-пайплайна к его джобе с максимальным `end` и продолжить путь оттуда. Когда внутри downstream у джоб закончатся `deps`, вернуться к `deps` самой bridge-джобы.
3. Среди `deps` текущей джобы выбрать ту, у которой максимальный `end`, и сделать её текущей.
4. Повторять шаг 3, пока `deps` не опустеет.

Выход — упорядоченный список джоб и зазоры между ними. Зазор — разница между `end` зависимости и `start` следующей джобы, включая `queued`. Эти зазоры тоже задерживают пайплайн, поэтому их показываем отдельно.

При равных `end` выбирается джоба, которая раньше встречается в ответе API. Так результат воспроизводим.

`critical-path.mjs` не импортирует других модулей. `render.mjs` подставляет его в HTML без изменений, поэтому интерфейс пересчитывает путь при клике по стейджу без второй реализации.

## Агрегат по N пайплайнам

- Ключ джобы — `стейдж + имя`. Шарды `parallel` объединяются в группу по имени группы, отдельные шарды показываются дочерними строками. Downstream-пайплайны агрегируются рекурсивно по имени bridge-джобы.
- Метрики джобы:
  - p50 и p90 для `start`, `end − start` и `queued`;
  - присутствие: в скольких из N пайплайнов джоба запускалась;
  - среднее число ретраев;
  - доля пайплайнов, где джоба лежала на критическом пути всего пайплайна.
- Метрики стейджа («до конца стейджа», длина) и общая длина пайплайна сначала считаются в каждом пайплайне отдельно, затем из них берётся перцентиль. Складывать перцентили джоб нельзя.
- Перцентиль считается методом nearest-rank по отсортированным значениям.
- Все N деревьев встраиваются в HTML. Из панели деталей можно открыть любой пайплайн в режиме одного пайплайна.

## Интерфейс HTML

Один файл с инлайновыми CSS и JS, данные встроены как JSON. Внешних запросов нет, поэтому файлом можно делиться.

- **Шапка.** Проект, ref, ссылка на пайплайн или строка вида «агрегат: 50 пайплайнов master, 47 success». Общая длина. Ось времени с делениями. В агрегате — переключатель p50/p90.
- **Левая колонка — дерево.** Кнопка ▸/▾ и число потомков у каждого узла. В строке стейджа: `длина 3m12s · до конца 14m05s`.
- **Центр — водопад.**
  - Полоски — `div` с `left` и `width` в процентах от оси.
  - Цвета: стейдж — жёлтый, джоба — по статусу, очередь `queued` — серый сегмент перед полоской, `allow_failure` — оранжевый, прошлые попытки — бледные.
  - Длительность подписана справа от полоски.
  - У джоб на критическом пути есть обводка, зазоры ожидания нарисованы пунктиром.
  - В агрегате сплошная часть полоски идёт от p50 `start` до p50 `end`, а «ус» — до p90 `end`.
- **Правая панель — детали по клику.**
  - Для одного пайплайна: имя, стейдж, статус, start/end, `queued`, длительность, `deps`, попытки, ссылка в GitLab.
  - Для агрегата: p50/p90, присутствие, доля на критическом пути, список значений со ссылками на пайплайны.
- **Управление.**
  - Клик по стейджу пересчитывает критический путь до конца этого стейджа.
  - Ctrl + колесо мыши масштабирует ось.
  - Esc закрывает панель.
- **Тема** светлая и тёмная через `prefers-color-scheme`.

## Тесты

`node --test`, без зависимостей.

- `model.test.mjs` — обезличенная фикстура реального GraphQL-ответа превращается в дерево. Проверяются границы стейджа, ретраи в `attempts`, `manual` без времени и отсчёт времени downstream от корня.
- `critical-path.test.mjs` — синтетические графы: цепочка, ромб, джоба без `needs`, путь через bridge в downstream и обратно, равные `end`.
- `aggregate.test.mjs` — перцентили, объединение шардов, «до конца стейджа» по каждому пайплайну (отличается от суммы перцентилей), присутствие.
- `gitlab.test.mjs` — пагинация и ошибки 401/403/404 на подменённом `fetch`.

HTML-шаблон автотестами не покрывается. Его проверяем вручную на двух пайплайнах: `litres/monorepo` с downstream и шардами и одном проекте без `needs`.
